# Subsystem audit — 2026-10-28

This records a source review and targeted regression testing, not a claim that
all possible resource lifetimes or query plans have been proved correct.
The public setup docs describe supported behavior; this file tracks findings
and follow-up decisions.

## Authorization and finite queries

The production authorization planner is **rule-based**, with no statistics,
cost model, join flipping, or physical join-order search. It enumerates grant
paths to the requested type, prunes unrelated branches, and inserts compatible
caller predicates at the grant site. `eq`, `ne`, `in`, `contains`, `like`, and
`ilike` have translations; partial AND narrowing is safe, whereas OR/NOT require
complete translations. Ordered scalar comparisons are conservatively left out
because physical and logical missing/scalar comparison semantics differ.
Policy windows and singular cardinality are barriers: pushing a predicate
through either can change which rows the policy grants. Caller sorting/windowing
happens after grant union and field masking. A private eager evaluator and an
independent domain oracle test the optimized evaluator.

Relevant code: `ontology-backend/src/policy/{planner,view,indexes}.ts` and
`ontology-backend/src/policy.test.ts`.

### Post Approval example, including actual source calls

Policy, expressed schematically using the existing Query IR helpers:

```ts
sub("approval", {
    from: { source: { objectType: "PostApproval" }, binding: "a" },
    where: eq(field("a", "id"), context("approvalId")),
    select: [
        selectField("id", field("a", "id")),
        sub("bids", {
            from: { source: { objectType: "Bid" }, binding: "b" },
            where: eq(field("b", "approvalId"), field("a", "id")),
            select: /* id, approvalId, status, rank */ [],
        }),
    ],
});
```

A separate root can grant all Posts. With authenticated context
`{ approvalId: "approval-42" }`, the caller requests Bids where status is Waiting,
ordered by rank descending with limit 1. The rewritten policy keeps the
PostApproval → Bid path, inserts `b.status = "Waiting"` into its Bid selection,
and drops the unrelated Post root. Its source calls are equivalent to:

```sql
SELECT * FROM PostApproval WHERE id = 'approval-42';
SELECT * FROM Bid
WHERE approvalId = 'approval-42' AND status = 'Waiting';
```

These are parameterized adapter subset requests, not SQL strings generated by
the authorization planner. It then masks fields, sorts, and returns the caller's
first row. It does **not** put that final limit on the upstream Bid call.
The test named “narrows a token's Post Approval/Bid grant…” checks the calls,
returned rows, and agreement with the eager oracle. A request by Bid ID still
starts from PostApproval; choosing Bid first would require a different planner.

The protocol already supports **finite full Query documents**, not just subset
loads. The executor lowers supported expressions/correlations to source scans;
each scan is authorized through the policy view. Complex expressions can require
residual evaluation and repeated correlated loads. This is not arbitrary
whole-document algebraic rewriting or server IVM. Query functions are separately
checked capabilities; arbitrary computed function results are not automatically
row-filtered.

## Error channels and recovery

`BackendError` is a Schema-tagged expected error, with shared wire encoding and
hook-specific kind aliases. In an Effect generator, `yield* new BackendError(...)`
fails in the typed error channel, just as `yield* Effect.fail(error)` does.
**Throwing** the same instance inside an Effect does not provide that guarantee:
it can become a defect. Pure helpers may throw when their Effect callers wrap
those calls with `Effect.try`.

| Failure                                           | Expected consumer action                                                                              |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Unauthenticated                                   | Ask for/recover caller credentials; upstream identity failures are projected separately.              |
| Forbidden / NotFound                              | Show permitted detail; do not retry blindly.                                                          |
| ValidationFailed                                  | Present permitted parameter issues and paths; preserve validate/apply distinction.                    |
| InvalidRequest / InvalidConfiguration             | Fix caller input or deployment configuration.                                                         |
| RateLimited / retryable Unavailable               | Respect retry delay; action outcome is a separate fact.                                               |
| Unknown action outcome                            | Reconcile a saved receipt or use safe idempotent recovery; require explicit decision where necessary. |
| HistoryExpired                                    | Refresh the base snapshot, preserving outbox.                                                         |
| SessionExpired / SessionReplaced                  | Acquire a new session, preserving unresolved work.                                                    |
| ViewReplaced                                      | Acquire the current selection.                                                                        |
| InvalidResponse / SourceMismatch / SchemaMismatch | Stop the delivery path and expose the incompatibility; do not pretend this is ordinary invalid input. |

The server projects immediate errors and recorded action failures before children
can inspect them. The shared classifier removes provider messages/bodies from
public errors, carries redacted causes internally, and distinguishes retry facts
from disclosure policy. Custom disclosure cannot change execution/retry facts.

### Fixed in this audit

- Public `policyView` construction now returns an Effect; missing/invalid policy
  configuration is a typed `InvalidConfiguration` failure, tested via `Effect.result`.
- LiveOntology backend construction normalizes failures, and missing persistence
  configuration uses `InvalidConfiguration` rather than an ordinary Error.
- A non-advancing provider change page is `InvalidResponse`, not `HistoryExpired`.
- Blob metadata lookup propagates auth, permission, unavailable, malformed-response,
  and other failures. Only explicit `NotImplemented` permits fallback to bytes;
  lack of a metadata capability also permits fallback. Regression tests cover
  four error kinds without calling byte download.

### Remaining error follow-ups

- Adapter sync loops record failed loads in diagnostics but retry on the next
  wake/poll even for some nonretryable errors. They do not yet have the same
  comprehensive controller/recovery decisions as protocol delivery. Separating
  one forbidden demand from global transport/auth failure needs explicit design;
  stopping every demand on one query failure would also be wrong.
- An adapter-level watch stream that terminates with an error can leave polling
  as the repair path rather than being reacquired by a common supervisor. The
  native Foundry physical watcher has its own reconnect loop, but that is not a
  universal adapter guarantee.
- Some installation lifecycle/configuration failures still use a broad
  Unavailable wrapper. Blob/collection SDK lifecycle misuse can still reject
  with an ordinary Error. These should not be confused with action validation.
- Full CI passes, but the workerd transport tests still log disconnect-related
  unhandled-promise exceptions and NDJSON body warnings. Their origin and whether
  they represent avoidable transport noise need separate triage; passing tests
  do not establish that these messages are harmless.
- Maintenance catches intentionally preserve successful action outcomes, but
  reporting is inconsistent: some log warnings, others only expose a failed
  span or silently wait for later maintenance. A common maintenance health view
  would make failures actionable without turning a committed write into failure.

## Cancellation and demand ownership

TanStack `loadSubset` options remain distinct acquisitions even when predicates
are equal. An already-aborted load does not acquire a lease. Later abort/unload
closes that acquisition's child scope, removes its signal listener, interrupts
its ready/observe work, and releases retention. Cleanup waits for releases.
Equivalent acquisitions share the replica's aggregate retention count.

This audit also closes a gap below the bridge: an adapter-backed background
subset snapshot now races the **last aggregate lease's release**. Closing one
consumer keeps shared IO alive; closing the last cancels that demand's IO and
lets the sync loop continue. Outbox submission/receipt reconciliation does not
belong to an individual UI consumer and is not canceled this way. Cancellation
cannot undo an already committed installation, and provider code must honor the
Effect/AbortSignal boundary for physical network cancellation.

Tests cover overlapping/duplicate TanStack demands and cancellation, plus a real
replica background load surviving one release and stopping on the last release.
Blob source signals now remain attached after header acquisition: abort closes
an unconsumed cold-read scope, cancels partial cache writing, and releases its
per-identity lock. Cached byte streams honor the signal during consumption too.

## Handle sources: below the UI adapter

The audit originally found two LiveOntology decorators: attachment sources and
opaque encrypted-property sources. Both now use the shared pure
`ontology-storage/src/ontology/sources.ts` read projection. LiveOntology no longer
maps/decorates these rows, and the old decorator modules and staged-write
attachment decoration are removed.

- Replica `get`, `loadSubset`, confirmed reads, snapshotSubset, and observeRows
  expose source-aware plain values before any TanStack collection receives them.
- Query execution derives locators from each source entity before selecting or
  aliasing fields. A projection can omit the primary key while retaining the
  original entity key/property on a returned handle. Authorization provenance
  still refers to the original policy-granted row identity.
- Native protocol subset responses use the same projection, including owned and
  proxy paths that do not run through a replica.
- The projection does not write tables, decrypt values, or mutate its input.
  Attachment containers are traversed using their declared schema; references
  and encrypted contents remain opaque. Device-encrypted private copies are not
  exposed as part of an encrypted handle.
- A source is a **locator, not a permission**. The server checks readable type,
  row, property, and re-finds that attachment ID inside that property. Nested
  attachment locations therefore need the owning top-level property, not a
  separately trusted nested path. Locators are re-derived for the current row.
- Explicit query-function outputs without entity provenance cannot acquire an
  invented source automatically. Providers/functions need to supply a valid
  locator when returning handles that require source-row authorization.

Plain objects are intentional. Proxies would complicate equality, transport
serialization and reactive tracking without improving authorization. Tests cover
shared nested handles, opaque encrypted values, replica reads/observations and
canonical stored rows, and authorized Query IR aliases that omit the primary key.

## DbClient and SSR

A scoped DbClient per LiveOntology view, and separate transaction-local clients,
are sensible ownership boundaries. Different principals/transactions do not share
a global DbClient. Its Promise cleanup is called from the Effect finalizer;
TanStack is a Promise/callback SDK and that is an appropriate integration boundary.

This is **not complete SSR support**. Issue-tracker deliberately uses `ssr: false`;
there is no library hydration handoff or example DbProvider/dehydrate wiring.
Required work before claiming SSR support:

1. Acquire an authenticated memory replica and view in the request's Effect scope;
   close it on request completion/abort. Do not start a process-wide user view.
2. Give logical collection identities a stable server/browser correspondence.
   Current runtime-owner/namespace IDs do not automatically match a new memory tab.
3. Transport selected safe rows or query-result snapshots with portable values.
   Exclude private credentials, decrypted caches, pending actions and optimistic
   state unless a separate explicit design authorizes those.
4. Seed the browser replica, or keep the hydrated query result authoritative until
   the replica is ready. Hydrating only a TanStack source collection can otherwise
   be followed by an empty replica reset that replaces those hydrated rows.
5. Test request/principal isolation, Temporal/handle serialization, cancellation,
   and the transition to live demand.

Keep DbClient for React/TanStack hydration and query ownership; an authenticated
replica seed would complement it rather than require replacing TanStack SSR.
There is no SSR acceptance test yet.

## State growth and maintenance

A scope finalizer bounds **lifetime**, not retained bytes during a long-lived
scope. Similarly, a TTL is not a total space budget. These are separate concerns.

### Reviewed bounds/ownership

- Replica row/blob retention uses precise demand, outbox dependencies, pins,
  age/grace policies and bounded sweep batches. Authoritative rows, unresolved
  outboxes, explicit pins and user-owned connection records intentionally persist.
- Client sessions and submission records have configurable limits, leases,
  acknowledgments and transactional expiry. Delivery subscriptions cap comparison
  records/bytes, frame sizes, subscriptions and ACK waits, and remove their
  process-local acknowledgment entries on release.
- Cached proxy demand leases have capacity, idle TTL and idle-entry replacement;
  active requests are never evicted to make a slot.
- Native attachment RPC transfers have concurrent/per-owner/byte/time limits,
  bounded queues and scope cleanup. Cold-read fanout has bounded buffers and
  per-identity reference-counted locks. Byte cache size remains governed by GC,
  not a global hard-byte admission limit.
- Tracing retains 500 spans by default and at most 100 displayed events per span;
  recent replica load diagnostics retain 100 records. Active subscriptions and
  React component attribution have corresponding release callbacks.
- The audit replaced historical per-user lock Maps in Connect and installations
  with scope-owned RcMap entries. Locks disappear after their last operation.
- Runtime connectivity and ConnectionMonitor state streams previously used the
  default unbounded callback queue. They now use sliding buffers of one state;
  the remote trace stream already did so.

### Remaining resource work

- No general memory/disk byte budget exists for replica rows, blob caches,
  authorization working sets or TanStack collection materialization. A broad
  active query can retain a large dataset. Full-query authorization can also
  materialize large grant results when narrowing is unavailable.
- The installation's successful-open cache lasts until explicit close or its
  scope closes; it has no practical automatic capacity/idle eviction. Hosts that
  dynamically open arbitrary ontologies must close them, rather than treat the
  installation as an unlimited request cache.
- Releasing the final TanStack demand releases replica retention but can leave
  the collection's last materialized rows until refresh/collection cleanup.
  Replica age GC does not itself impose a hard budget on that separate UI copy.
- Connect authority expiry is scheduled by `maintainConnect`, or explicitly by
  a serverless job/alarm calling `collectExpired`. Merely defining a TTL does not
  run maintenance. Owned HTTP servers have periodic maintenance; direct owned
  services also do cleanup proportional to writes and expose maintenance.
- Generic standalone SalesforceClient still exposes the older callback/Promise
  CometD CDC loop. It is not used by the native Salesforce ontology adapter and
  is not scope-joined Effect code; terminal re-handshake errors are swallowed.
  Remove that unused API or port it before advertising native CDC support.
- Query evaluation and provider pagination have no universal maximum work/rows
  budget. Delivery's record/byte bounds do not bound every finite query request.
- Infinite history/result retention is an explicit unbounded configuration,
  suitable only when the host intentionally wants that persistence.

## Effect and remaining layering

Installed Effect 4's complete AGENTS guide, its services/layer, acquire-release,
reason-error and managed-runtime examples, and the local Stream/RcMap APIs were
used for this audit. Lowercase static `.layer = Layer.effect(...)` is idiomatic;
capitalizing it would not improve lifetime management.

Native runtime construction, installations, Connect sessions, storage, replica
sync/delivery and the native Foundry watcher use Effects and scopes. Expected
errors should remain in `E`; finalizers own cleanup. Retryable failure, cancellation
and programmer defect must not be interchangeable.

We are **not literally Effect-only**. Promise/callback boundaries remain for
TanStack DB transactions, React, fetch/WebSocket/provider SDKs, crypto/keychain
APIs and the end-developer LiveOntology facade. Their resources must still belong
to an acquired scope. `destroy()` is a destructive storage operation, distinct
from normal scope cleanup; it should not run automatically on scope close.
The Foundry callback watcher facade is explicitly isolated as requested, with
its native implementation used by our adapter. No Effection/coordination-package
runtime dependency remains in workspace package manifests.

Potential further simplification: make the internal BlobManager acquisition
Effect-native and retain only the public attachment Promise facade. It currently
bridges to the already Effect-native BlobStorage and owns a child scope correctly,
but has more manual Promise/Scope plumbing than the rest of the engine. Similarly,
TanStack's transaction query bridge remains deliberate implementation machinery;
it is not a second persistence or outbox executor.
