## Tables

`ontology-storage` supplies row transactions and subset queries. Memory,
IndexedDB, and SQL implementations support the common interface. IndexedDB uses
user-space indexes and a subset planner; SQLite and PostgreSQL push supported
predicates and ordering into the database.

The SQL implementation currently uses a shared-row/JSON layout. Native application
columns and general schema migrations are future work.

## Attachment metadata and bytes

Blob metadata, aliases, reverse references, retention roots, and write/delete
intents share the transactional table store. External bytes can live in OPFS,
files, or object storage. A byte service reads, writes, and deletes immutable
storage keys using byte streams.

External IO cannot participate in a SQL or IndexedDB transaction. Durable intents
and generation checks make interrupted writes/deletes recoverable. Metadata is
published only after successful byte completion. Outbox roots and scoped readers
protect bytes while they are needed.

## End-developer API

```ts
const { attachment } = await ontology.attachments.create(file);
const source = await ontology.attachments.source(attachment);
```

Creation accepts Blob/File and streaming inputs. A streaming input carries
optional size, media type, and name. Unknown-length streams are supported;
resumable uploads and range caches remain future work.

## Browser placement today

In issue-tracker, tab attachment operations delegate to the SharedWorker over RPC.
The worker manages durable staging, upload, and cached bytes. The tab does not have
an independent durable attachment cache.

The connected-client composer currently installs the RPC attachment API directly
as `LiveOntology.attachments`. Applications do not select a special tab adapter:
they provide a connection to `createConnectedLiveOntology`, and its composition
contains `attachments: connection.operations.attachments`.

`source(handle)` obtains metadata and returns a lazy RPC byte stream from the
worker. `blob(handle)` deliberately collects that stream into a Blob. `create(input)`
streams the input to the worker, which stages it in its own attachment storage.
This applies to connected protocol clients, not a check for "is this a tab?".
The normal-child target can use local BlobStorage with its parent as the remote
byte provider. A cold miss in today's BlobManager finishes caching the remote
source before exposing the local read stream; progressive read-through and range
caching are future work. RPC streaming avoids collecting another Blob in the tab.

## Garbage collection

All replicas use the same age-based bounded mark-and-sweep for rows. Demand,
explicit pins, and pending-action dependencies are retention roots. Blob identity
retention and byte retention can differ, so cached remote bytes can be evicted
without losing an attachment's identity.

Protocol children collect confirmed rows and inherited overrides together as one
logical base, retaining their own action dependencies through parent inclusion.
An evicted base can be reloaded even when the parent revision is unchanged.
Selected snapshots also replace old imported membership. Action/session history
has separate bounded retention.

Independent protocol-child blob storage remains unfinished; connected clients
currently delegate bytes to the parent. See the
[GC rules and concrete examples](/docs/design/garbage-collection).
