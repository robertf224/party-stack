---
title: Authorization
description: Grant access to a graph of objects, hide properties, and bind action parameters.
---

Write down the data a person may see and the actions they may take. Party Stack
uses that policy for queries, cached reads, attachments, and actions, regardless
of how a screen asks for its data.

For example: **project administrators can see their projects and the forms inside
them, and can create new forms in those projects.** Express that relationship once.
A screen can then start from projects, forms, or revisions without rebuilding the
authorization join. Party Stack plans the reads and uses the backend's available
indexes and pushdown; the policy describes access rather than a particular SQL plan.

[Authentication](/docs/authentication) establishes who is calling. Authorization
uses that identity to decide what they can do. The examples below use `Project`,
`Form`, and `FormRevision`, linked by `projectId` and `formId`; projects have an
`adminIds` array.

## Declare context and its storage partition

```ts
import { o } from "@party-stack/ontology-spec";

const contextDefinition = {
    type: o.struct({
        fields: [
            { name: "userId", displayName: "User", type: o.string({}) },
            { name: "tenantId", displayName: "Tenant", type: o.string({}) },
        ],
    }),
    partition: [["tenantId"], ["userId"]],
};
```

`partition` determines which context values isolate local caches. Include all
identity fields needed to prevent different callers sharing private cached data.
Credentials stay in server services, outside the context returned to clients.

## Grant a project and its descendants

A read policy is a hierarchical query. Its selections grant the named properties
on matching objects, even when the client queries those objects from another root.

```ts
import * as q from "@party-stack/ontology/query";

const fields = (binding: string, ...names: string[]) =>
    names.map((name) => q.selectField(name, q.field(binding, name)));

const projectObjects = {
    select: [
        q.sub("projects", {
            from: { source: { objectType: "Project" }, binding: "p" },
            where: q.contains(q.field("p", "adminIds"), q.context("userId")),
            select: [
                ...fields("p", "id", "name"),
                q.sub("forms", {
                    from: { source: q.related(q.local("p"), "forms"), binding: "f" },
                    select: [
                        ...fields("f", "id", "name", "projectId"),
                        q.sub("revisions", {
                            from: { source: q.related(q.local("f"), "revisions"), binding: "r" },
                            select: fields("r", "id", "formId", "createdAt"),
                        }),
                    ],
                }),
            ],
        }),
    ],
};
```

This grants forms and revisions transitively through projects the user administers.
These sources follow declared ontology links (`forms`, `revisions`, `person`, or
`bids` in the examples). The link supplies both the target type and its join
predicate; `where` can add further restrictions. Add sibling roots for unrelated
public data. Policy selections use actual property names; UI query projections can use aliases and computations.

## Check an action

Give `createForm` a `project` parameter declared as an object reference:

```ts
// Include this field in createForm.parameters.
const projectParameter = {
    name: "project",
    displayName: "Project",
    type: o.objectReference({ objectType: "Project" }),
};
```

The caller supplies a Project primary key. `lookup` uses the parameter's declared
object type to read that project. Check its administrator list:

```ts
const targetProject = q.lookup(q.input("project"));
const canAdministerTarget = q.contains(
    o.Expression.getAt({ source: targetProject, path: ["adminIds"] }),
    q.context("userId")
);

const policy = {
    objects: projectObjects,
    actions: [
        {
            actionType: "createForm",
            check: canAdministerTarget,
            bind: [{ parameter: "createdBy", expression: q.context("userId") }],
        },
    ],
};
```

`check` is a boolean expression. A missing project or a caller absent from its
administrator list fails this check. It can inspect stored properties without
granting those properties to the caller.

The binding removes `createdBy` from the public action parameters and supplies
the authenticated value. An action without a successful rule is denied.
Query functions need their own `queryFunctions` rules as well.

### Additional implementation reads

An action or query-function rule can grant its owned implementation extra rows
and properties for that invocation:

```ts
queryFunctions: [
    {
        queryFunctionType: "quote",
        check: q.eq(q.context("role"), q.literal("buyer")),
        additionalObjects: {
            select: [
                q.sub("pricing", {
                    from: { source: { objectType: "PricingRule" }, binding: "price" },
                    where: q.eq(q.field("price", "product"), q.input("product")),
                    select: [q.selectField("discount", q.field("price", "discount"))],
                }),
            ],
        },
    },
];
```

These grants **add to** `policy.objects`. They do not replace it or grant those
reads to the caller's ordinary queries. The example assumes a `quote` function
with a `product` parameter; its owned handler can read the private pricing rule
and return a public total.

Action and function results currently follow their declared return types; object
policy does not redact arbitrary returned structs. Construct public results
explicitly. Additional implementation access is a trusted computation, so returning
the private discount would disclose it.

Owned backends run checks and mutations in one transaction. For an upstream
provider, your server checks its own policy before calling the provider; the
provider's permissions and transaction still apply.

## Bind the authenticated caller

```ts
import { makeOntologyServer } from "@party-stack/ontology-server";

const ir = { ...domainIR, context: contextDefinition, policy };
const openServer = makeOntologyServer({
    enableRealtime: true,
    kind: "owned",
    backend,
    ir,
    authenticate: (request) => authenticatedContext(request),
});
```

Acquire `openServer` once in the server Layer. `authenticatedContext(request)` is your
authentication Effect returning `{ userId, tenantId }` for each request; a missing or invalid
session must fail. The server owns each request's policy binding. A cached proxy enforces the same policy on its final read
path, including cache hits.

## Grant a conditional property

Add a conditional selection inside a Form query:

```ts
q.selectCase({
    branches: [
        {
            condition: q.eq(q.context("role"), q.literal("admin")),
            select: fields("f", "internalNotes"),
        },
    ],
});
```

Declare `role` in the context type for this example. A context-only condition
can remove a property from the public definition. A condition depending on each
row makes that property optional; inaccessible values are omitted.

## Project a provider for a token

A public form might use a Post Approval token instead of a signed-in user.
Replace the upstream context and policy with your token contract:

```ts
import { Effect } from "effect";

const tokenIR = {
    ...upstreamIR,
    context: {
        type: o.struct({
            fields: [
                {
                    name: "approval",
                    displayName: "Approval",
                    type: o.objectReference({ objectType: "PostApproval" }),
                },
            ],
        }),
        partition: [["approval"]],
    },
    policy: {
        objects: {
            select: [
                q.sub("approval", {
                    from: { source: { objectType: "PostApproval" }, binding: "a" },
                    where: q.eq(q.field("a", "id"), q.context("approval")),
                    select: [
                        ...fields("a", "id", "status"),
                        q.sub(
                            "person",
                            {
                                from: { source: q.related(q.local("a"), "person"), binding: "p" },
                                select: fields("p", "id", "name"),
                            },
                            "one"
                        ),
                        q.sub("bids", {
                            from: { source: q.related(q.local("a"), "bids"), binding: "b" },
                            select: fields("b", "id", "postId", "status"),
                        }),
                    ],
                }),
                q.sub("posts", {
                    from: { source: { objectType: "Post" }, binding: "post" },
                    select: fields("post", "id", "name"),
                }),
            ],
        },
        actions: [
            {
                actionType: "submitBid",
                check: q.eq(
                    o.Expression.getAt({
                        source: q.lookup(q.context("approval")),
                        path: ["status"],
                    }),
                    q.literal("open")
                ),
                bind: [{ parameter: "approval", expression: q.context("approval") }],
            },
        ],
    },
};

const openTokenServer = makeOntologyServer({
    kind: "proxy",
    backend: foundryBackend,
    ir: tokenIR,
    authenticate: (request) =>
        verifyFormToken(request).pipe(Effect.map((token) => ({ approval: token.approvalId }))),
});
```

This form leaves `enableRealtime` unset: it serves finite reads and submissions
without watches, change feeds, or client replication sessions. Calling its action
returns a completion receipt; it does not wait for any watcher.

The caller can read its approval, the person's name, its bids, and the public list
of posts. It can submit a bid only while that approval is open, with the approval
parameter supplied by the server. The server's provider
credentials are independent of the public token context. `verifyFormToken` is an
application Effect that verifies the token and returns its approval ID.

## What clients receive

`Describe` sends the policy-projected IR and the declared context values. The
policy itself, including read predicates, action checks and binding expressions,
stays on the server. Bound action parameters are removed from the public signature;
the server supplies their values during execution.

Clients can call `ontology.actions.submitBid.validate(parameters)` before submitting.
Parameter constraints and projected defaults can support local validation, but
policy checks are not currently exported as client validation hints. Forwarding a
provider's existing definition does not turn its authorization rules into such hints.
Submission always checks the server policy again.

For the Post Approval token above, clients see the allowed PostApproval, Person,
Bid and Post properties and the permitted actions. They do not receive unrelated
types/properties or the upstream service user's context. Context-only conditions
can remove properties/actions from the definition. Row-dependent conditions stay
server-side; conditionally present properties become optional in the public schema.

Visible definitions still carry names, labels and metadata. Valid projected action
logic/defaults can also be sent for local evaluation; computations incompatible
with the public definition are omitted. This projection does not scrub arbitrary
provider metadata or documentation. Remove private annotations/provider details
when constructing the form IR if they should not be public.

Treat the declared context as public: a bound approval ID is included in the token
example. Keep bearer tokens, token secrets and service credentials outside it.

Read [Authorization boundaries](/docs/authorization-boundaries) for receipt
visibility, error projection, watches, and privileged diagnostics.
