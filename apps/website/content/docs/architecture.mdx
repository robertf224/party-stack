## The pieces

| Component                       | Responsibility                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------------- |
| `ontology-spec`                 | Portable definitions, values, relationships, expressions, lenses, and generation.      |
| `ontology-storage`              | Ontology-aware transactions, row queries, indexes, overlays, and blob metadata.        |
| `ontology-backend`              | Provider operations, standard errors, receipts, and protocol state types.              |
| `ontology/tanstack`             | Scoped TanStack DB collections, subset demand translation, and diagnostics.            |
| `ontology-replica`              | Local base, pending actions, optimistic projection, reconciliation, and demand.        |
| `ontology-server`               | Expose ontology operations and replication across a process/network boundary.          |
| `ontology`                      | Application-facing objects/actions and the composition of a replica into LiveOntology. |
| `runtime` and platform packages | Scoped platform storage, connectivity, private services, and lifecycle.                |

## Where state lives

| Location                    | State                                                                        |
| --------------------------- | ---------------------------------------------------------------------------- |
| Owned authoritative backend | Committed object rows, action receipts, and a change journal in its storage. |
| Intermediate replica        | Imported state, its own pending outbox, and an optimistic overlay.           |
| Browser SharedWorker        | Persistent device replica using IndexedDB tables and OPFS bytes.             |
| Browser tab                 | Memory replica of selected parent state, plus its own unresolved actions.    |
| TanStack DB                 | Materialized collections and query results supplied by the local replica.    |

An intermediate's acceptance means it has taken responsibility for an action.
That is distinct from authoritative confirmation. The child removes its duplicate
prediction when it imports a parent update that includes that action.

## Server roles

- **Owned server:** executes authoritative actions against storage it controls.
- **Proxy server:** forwards reads and actions upstream.
- **Cached proxy server:** serves confirmed reads through an internal replica;
  actions forward upstream without entering the read cache's outbox.
- **Replica server:** can durably queue actions and publish their optimistic
  results before its own upstream confirms them.

A Durable Object can take any of these roles. Being a worker or a server does not
by itself decide whether a component is authoritative.

## Two upstream acquisition paths today

A replica uses the committed backend contract for providers such as Foundry and
for owned, proxy and cached-proxy servers. It loads subsets and can consume
committed change pages when that backend exposes a journal. Change watchers are
wake-up hints; journal pages carry the actual committed row changes.

An intermediate replica server additionally exposes speculative state, including
inherited predictions and action progress. Connected children currently receive
change notifications and then read selected replacement snapshots. This path does
not yet deliver incremental patches. Both paths use the same Replica, local
BlobStorage and retention machinery.
