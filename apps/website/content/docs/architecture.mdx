## Where state lives

| Location                    | State                                                                        |
| --------------------------- | ---------------------------------------------------------------------------- |
| Owned authoritative backend | Committed object rows, action receipts, and a change journal in its storage. |
| Intermediate replica        | Imported state, its own pending outbox, and an optimistic overlay.           |
| Browser SharedWorker        | Persistent device replica using IndexedDB tables and OPFS bytes.             |
| Browser tab                 | Memory replica of selected parent state, plus its own unresolved actions.    |
| TanStack DB                 | Materialized collections and query results supplied by the local replica.    |

An intermediate's acceptance means it has taken responsibility for an action.
That is distinct from authoritative confirmation. The child removes its duplicate
prediction when it imports a parent update that includes that action.

## Server roles

- **Owned server:** executes authoritative actions against storage it controls.
- **Proxy server:** forwards reads and actions upstream.
- **Cached proxy server:** serves confirmed reads through an internal replica;
  actions forward upstream without entering the read cache's outbox.
- **Replica server:** can durably queue actions and publish their optimistic
  results before its own upstream confirms them.

A Durable Object can take any of these roles. Being a worker or a server does not
by itself decide whether a component is authoritative.

## Receiving updates

Provider adapters load subsets and, where available, committed change pages.
Their watchers wake the replica so it can acquire fresh data.

Native servers can stream a selected snapshot followed by incremental batches.
Owned and cached-proxy servers publish committed rows. An intermediate replica
server also publishes inherited predictions and selected action progress.
A child installs each complete batch in one storage transaction, rebases its own
outbox, and then acknowledges the delivery. Updates to rows, inherited overrides,
action handoff, coverage and the installed position become visible together.

The server reevaluates the selected subsets and compares their keyed results.
It stores bounded comparison/staging state in its table store. Each subscription
has one outstanding batch; changes while a client is slow are coalesced. Closing
the Scope releases that state. Reconnecting starts a fresh selected snapshot while
the child's local outbox remains intact.

Native HTTP and worker servers accept `deliveryStrategy`:

- `"auto"` (default) selects delivery from the available source capabilities.
- `"snapshot"` uses invalidation hints and finite selected reads, without selected
  patch streams or journal delivery on that endpoint.
- `"incremental"` requires native selected delivery and reports `NotImplemented`
  during connection setup if the source cannot provide it.

For example, add `deliveryStrategy: "snapshot"` to `makeOntologyServer(...)` or
`serveOntologyWorker(...)` options. The setting controls outgoing delivery; a
cached/intermediate server's upstream synchronization is configured independently.
The `delivery` option continues to configure patch capacity/frame/acknowledgment
bounds. Server query maintenance currently recomputes selections; IVM maintenance
is future work and has no configuration flag yet.
Snapshot mode still retains the ordinary speculative action/session bookkeeping
when serving a replica; it removes selected-delivery comparison state, not outboxes
or normal row/blob retention.

Local TanStack collections consume composed row changes. Simple predicates apply
changed keys directly; sorted/limited windows query local storage for their new
membership. Unchanged rows are not rewritten into the collection. Both upstream
paths use the same Replica, local BlobStorage and retention machinery.

## Optimistic actions and confirmation

The replica composes upstream state with an overlay produced by replaying its
pending local actions. Incoming changes update upstream state, settle confirmed
actions and rebuild the remaining overlay in one local transaction. An outbox
need not be empty before incoming state can be incorporated.

A snapshot can already contain an action while that action is still pending
locally. For example, a base count of 5 plus a pending increment displays 6. If a
snapshot containing that increment installs 6 while the increment remains pending,
replay would incorrectly display 7.

Adapter-backed replicas conservatively coordinate source publication with action
submission and confirmation. This follows the action lifecycle, not inspection of
snapshot values or automatic detection of independent rows:

- With a receipt cursor and change journal, catch up to the matching commit and
  settle the action alongside its confirmed changes.
- Otherwise, read back the affected objects after saving the committed receipt.
  Install those rows, remove the pending action and replay remaining actions
  atomically. Failed read-back retries confirmation without resubmitting the action.
- Ordinary state refresh defers while an action is sending or a committed receipt
  still awaits reconciliation. The coordination gate currently covers a whole
  outbox drain pass, including network IO, so sustained writes can delay refresh.

Read-back must observe the committed write. A successful receipt alone does not
make a stale provider read safe; adapters without a cursor rely on the provider's
read-after-write behavior. Lost submission replies follow unknown-outcome recovery
rather than being treated as rejection.

Speculative-parent delivery carries explicit action acceptance/state information;
children settle their duplicate predictions as part of installing parent batches.
State refresh and outbox processing have independent scoped lifetimes. Canceling
UI demand never owns or cancels the background action worker.

## Platform Runtime

`Runtime` is the Effect service identifier. `RuntimeService` is its acquired
implementation: Tables, Effect byte IO, encryption keys, connectivity and browser authentication.
Platform packages provide configured Layers. `RuntimePartition` supplies the
storage owner/namespace as an Effect requirement; `Runtimes` uses LayerMap to
share active acquisitions of the same partition and release the final lease.
`RuntimeOptions` is only construction input for platform implementations.
Trace recording is composed by each ontology replica through the normal Effect
Tracer, independently of platform storage and Runtime partition acquisition.

Runtime does not expose an adapter lookup, captured Context, owning Scope,
storage broadcasts, actor liveness or host-election hooks. Consumers request
services and Scope through Effect. Normal Scope cleanup closes platform resources;
`Runtime.destroy` is a separate Effect for explicit local-data deletion after closure.

## Persistent web ownership

One designated process owns each persistent replica namespace. Issue-tracker uses
one SharedWorker per installation: it owns Connect records, token refresh, backend
sessions, persistent row/blob storage and its ontology hosts. Pages do not open
those tables. Installation controls, connection snapshots and ontology operations
use Effect RPC over the worker connection. Browser popup/callback presentation
stays in the page; PKCE state and credential exchange stay in the owner.

Tabs use ordinary memory replicas with local byte caches. The worker retains
scoped ontology endpoints through LayerMap while requests/subscriptions use them;
idle endpoints close after the configured idle period. Browser SharedWorker identity
provides process placement. There is no additional runtime Web Lock election or
silent persistent fallback after a failed worker connection.

On exclusive-owner startup, the replica removes abandoned query/read leases.
Pins, object references and pending action dependencies survive. Blob storage
tracks active local IO internally and recovers durable intents after a restart;
it needs no public Runtime actor-liveness capability. Ordinary row/blob GC then
uses the same retention rules in web, Node and Expo.

## Demand retention

A replica can keep unused subsets warm for reuse across requests or navigation:

```ts
const replica =
    yield *
    makeReplica({
        ...options,
        demand: { idleMs: 60_000, maxSubsets: 128 },
    });
```

The default idle timeout is zero; the default cap is 1,024 distinct subsets.
The last consumer's release starts the idle timer. Reuse renews it; expiry
releases the upstream subscription and retention root. At capacity, the oldest
idle entry is evicted first. Active entries are protected, and excess distinct
work receives `RateLimited` if every slot is active. Cached-proxy servers use this
replica policy directly, without a separate server-side demand cache.

This controls demand lifetime, not data size. Row/blob garbage collection has its
own age and retention rules. TanStack live-query GC can retain UI demand; avoid
unintentionally stacking that lifetime with a long replica idle timeout.
